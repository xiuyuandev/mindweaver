# M12d · 20k 打字的最后一公里：索引不再每轮重建（打磨轮 14）

> 依据：账本 §3 第 7 条「20k 增量布局」的下一步；预算 `docs/08` §2 **P7：改 1 节点 ≤ 16ms（布局函数计时）**。
> 前作：`shots/x100/M12b/`（分阶段账）、`shots/x100/M12c/`（真增量，p95 16.9 差 0.9ms）。
> 状态：`已实现`。P7 的「布局函数计时」口径 **p50 14.49 → 13.00、p95 16.07 → 13.90、max 16.67 → 15.55**，
> **p95 首次达标**；端到端（命令 + 重建）中位 18.3 → 16.7ms，**仍超 16ms**，如实记账。

## 1. 这一轮解决什么

M12c 把「改一个字」的 20k 重建压到 `[scene] total` p50 15.5 / p95 16.9ms，差 0.9ms 过不了 P7。
它留下的账逐段是：`resolve 2.9（内容指纹）/ layout 7.0（collect 2.6 + measure 1.7 + bounds 1.2）/
index 1.2 / nodes 1.5 / order 1.0 / edges 0.3`。

其中 **`index` 是纯浪费**：它是 `ids → 下标` 的哈希表，而 `ids` 在「只改一个字」时逐字相同。
场景却每轮按最终 `ids` 重建一遍——两万次 `String` 克隆 + 两万次插入，实测 1.1–1.3ms。

## 2. 非目标

- **不动 `Scene::ids` / `Scene::index` 的公开类型**（仍是 `Vec<String>` / `HashMap<String, u32>`）：
  `Arc<str>` 化能再省 ~1ms，但要改 150 处调用点，单独记账（见 §7）。
- 不改 `measure` / `bounds` / `order` 的算法。
- 不改概念图路径的索引语义（自由主题合并后索引确实会变）。
- 不加依赖、不改 `.zmind`。

## 3. 两刀

### 3.1 索引：没并进自由主题就沿用布局那份

`compute_layout` 本来就产出 `Layout::index`，但场景层把它丢掉了（`index: _`）——
因为合并自由主题会把浮动概念追加进 `ids`，那时索引才作废。现在：

```rust
let main_len = ids.len();
// …合并自由主题（必要时 ids.extend）
let index = if ids.len() == main_len {
    main_index            // 没有并进任何自由主题 → 布局那份就是最终索引
} else {
    /* 重建 */
};
```

20k 树与 20k 打字都是「一颗浮动主题都没有」的情形，于是 1.2ms 直接变 0。

### 3.2 collect 的栈不再克隆 id

遍历用的是显式栈，原来每个孩子入栈都 `c.clone()` 一份 `String`：
20k 树等于两万次纯粹为了「等会儿再查一次」的分配。改成栈里放 `&Node`（文档是不可变借用，
生命周期天然够用），`ids` 里那份克隆保留——它是 `Layout::ids` 的真正内容，不能省。

## 4. 量法

- 两个 release 二进制交替跑（同一份 `perf_scene`，A = 改前、B = 改后），各 3 轮取中位。
- 两条口径都记：
  - **P7 口径**（`docs/08` §2 写的是「布局函数计时」）：`MW_LAYOUT_LOG=1` 下 `[scene] total`，
    只统计 `reused=19999` 的那些（缓存路径），40 次一轮取 p50/p95；
  - **端到端**（用户感受到的）：`perf_scene` 的「20000 改字重建(缓存)」，含 `Command::SetText` 与账本克隆。

## 5. 实测

### 5.1 P7 口径（`[scene] total`，40 次改字）

| 版本 | p50 | p95 | min | max |
| --- | --- | --- | --- | --- |
| A 改前 | 14.49 | **16.07** ❌ | 12.91 | 16.67 |
| B 改后 | **13.00** | **13.90** ✅ | 11.08 | 15.55 |

p95 首次进 16ms，且最大值（15.55）也在预算内；改前有两成样本越线。

### 5.2 端到端（含命令与账本克隆）

| 版本 | 中位（3 轮） | p95（3 轮） |
| --- | --- | --- |
| A 改前 | 18.3 / 18.5 / 17.9 | 19.6 / 20.4 / 19.9 |
| B 改后 | **16.7 / 16.9 / 16.4** | **18.4 / 18.4 / 17.8** |

省下的约 1.5–1.9ms 与账上一致（index 1.2 + collect 的一部分）。端到端仍差约 1ms 到 16ms 线，
差额在 `[scene]` 里程碑之外：账本克隆（两万个 `SceneNode`，约 1.2–1.5ms）与命令本身。

### 5.3 改后分阶段（缓存路径，中位）

```text
[scene] n=20000 total≈13.0  resolve≈2.6  layout≈6.5  index=0.00  nodes≈1.5  order≈1.0  edges≈0.3
[layout] n=20000 total≈5.8  collect≈2.4  measure≈1.6  csr≈0.14  bands≈0.13  place≈0.24  bounds≈1.15
```

## 6. 单测

`the_scene_index_agrees_with_ids_whether_floaters_are_merged_or_not`：

- 树（无自由主题，走沿用分支）与概念图（并进浮动概念，走重建分支）两种文档，
  都断言 `index.len() == ids.len()` 且每个 id 的下标指回自己；
- **做过变异检查**：把条件改成无条件沿用，这条测试立刻红（`索引与节点表必须一样长（conceptMap）`）；
  改回来即绿——挡的正是「并进自由主题却沿用旧索引，`parent` 静默变成 `None`」。

## 7. 未做 / 风险

1. **端到端还差 ~1ms**：差额在账本克隆（`memo_nodes = nodes.clone()`）与命令，不在 `[scene]` 里。
   要消掉得让 `SceneMemo.nodes` 与 `Scene.nodes` 共享一份（`Arc` + 复用），是 API 级改动。
2. `Scene::ids` / `Scene::index` 仍是 `Vec<String>` / `HashMap<String, u32>`：`collect` 里那 20k
   次 `String` 分配（约 0.8ms）还在。`Arc<str>` 化能连同 `index` 的建表一起省，但要动 ~150 处调用点。
3. `bounds`（1.15ms）与 `order`（1.0ms）仍是每轮 O(n)：文字改了盒子会变，位置与绘制顺序**确实**
   可能变，不能整段复用；要省得做成增量更新。
4. 概念图不走这条复用（浮动概念会把索引作废），节点数少，影响可忽略。
5. 只在合成语料（20k 树）与 1080p / ppp 1.0 上量。
