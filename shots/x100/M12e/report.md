# M12e · 撤销/重做走缓存账：两代账 + 一句「先试上一代」（打磨轮 15）

> 依据：账本 M12 行的 P9 残账——20k 撤销/重做 41–43ms（P9 预算 30ms，超）；
> 预算 `docs/08` §2 **P9：撤销/重做 ≤ 30ms**。
> 状态：`已实现`。**文字撤销/重做（缓存路径）20k 中位 15.7 / 15.3ms、p95 17.5 / 17.0ms——P9 达标**；
> **结构撤销**（加节点 → 撤销）第一步做到 28.9 / 31.1ms（差 1ms），**第二步**（同日、同一轮补的：
> 「对不上指纹的那一代也不能扔」）落到 **中位 15.8 / p95 17.1ms——P9 达标**。

## 1. 这一轮解决什么

应用的 `Ctrl+Z` 走的就是 `build_scene_cached`，但 `SceneCache` 只留**一代**账（上一次的内容）。
撤销把文档退回到上一次**之外**的那份内容：

- 改一个字再撤销：退回到「改之前」——布局账按**内容指纹**（不含文字）比对仍算「匹配」，
  两万个盒子里只有那一个字的账对不上，实测 ~15.8ms，**本来就不用修**；
- 加一颗节点再撤销：可见节点序列变了，`ids_fp` 对不上 → 当前代的账整份作废 →
  **全量重建 43ms**（`[scene]` 里 resolve 8 + layout 20 + nodes 7）。

后一种才是撤销最常见的形态之一（建错一颗、删错一段），而它 43ms 里 25ms 是纯浪费：
「上一代」的账就在手里，只是没留下来。

## 2. 非目标

- 不改 `Scene::ids/index` 的公开类型，不动 `Document::undo` 的语义。
- 不做「撤销快照」（整份 `Scene` 快照换入换出）——那是更大的 API 改动。
- 概念图路径不走账本（既有取舍），不覆盖。
- 不给「撤销相机」（整理布局的取景回退）——那是账本另一行。

## 3. 设计

### 3.1 账本留两代

`SceneCache` 加 `prev_memo` 一槽：`put_memo(memo, spare)` 把这次**没用上的**那一代退成「上一代」。
关键的一行（第一版实现漏了，当场被单测抓住）：只有一代候选时，**这一轮建账用掉的那份也要退成上一代**——
内容指纹不含文字，「改了一个字」时它照样算「匹配的当前代」，可它代表的正是**改之前**的内容，
撤销要退回的就是它。

内存账：多留一份账 ≈ 两万个 `SceneNode` + 盒子表（20k 实测数十 MB 级），桌面机可接受，此处如实记。

### 3.2 撤销/重打一遍招呼：「先试上一代」

撤销/重做会退回上一代内容，先按当前代去试多半白跑一遍布局（20k 上 3–4ms）。
`SceneCache::prefer_previous()` 让下一次重建先试上一代；`Canvas::undo/redo` 在 `rebuild()` 前打招呼。

两代都要试时按「复用得更全」者胜：一代只差一颗（正是刚改/刚撤的那颗）就认它，
不再试另一代——另一边几乎必然更差，多跑一遍布局是白付。

## 4. 量法

`perf_scene` 新增三段（全部走 `build_scene_cached`，即应用的真实路径；改前的例程量的是
`build_scene` 无缓存路径，那不是 `Ctrl+Z` 的真实手感）：

- `撤销重建(缓存)`：改字 → 重建 → 撤销 → 重建，量后一次；
- `重做重建(缓存)`：重做 → 重建（再撤回，保持循环可复跑）；
- `结构撤销重建(缓存)`：加一颗节点 → 重建 → 撤销 → 重建，量后一次。

## 5. 实测（同机 release，20k 合成语料）

| --- | --- | --- | --- |
| 20k 撤销重建（文字） | 43.1（无缓存 42.9 p95 46.5） | **中位 15.7 / p95 17.5** | P9 30ms ✅ |
| 20k 重做重建（文字） | 42.8 | **中位 15.3 / p95 17.0** | ✅ |

## 6. 单测

`undo_hits_the_previous_generation_of_the_memo`：改字 → 重建 → 撤销 →（`prefer_previous()`）重建，
断言退回的行数据与撤销前是**同一次测量**（`Arc::ptr_eq`）。这条测试在第一版实现上**当场红**：
把「用掉的当前代」直接丢掉、只留 `spare`，撤销就永远命中不了——这正是设计的核心一行。

## 7. 未做 / 风险

1. **结构撤销差 1ms**（28.9 / p95 31.1 vs 预算 30）：账上还有一笔可省——结构变化时内容指纹变了，
   `resolve`（8ms）整段重算其实是白付（样式没变）。把它和内容指纹合并成一次遍历是下一刀。
2. 账本内存翻倍（两代）。20k 下是几十 MB 量级，没有内存预算条目对它约束；若要省可以按节点数封顶
   （超过 50k 只留一代），本轮不做。
3. 「重做」循环里每次重做后又撤回，是为了让循环可复跑（连续重做 40 次会到头）；测的是单次重做的成本。
4. 概念图与卡片页不走账本，撤销仍是全量（概念图节点少，卡片页是另一套管线）。
5. 实机手感（Ctrl+Z 按住连撤的帧率）没量过——离屏只有单次成本。

## 8. 第二步（同日补）：对不上指纹的那一代也不能扔

第一步落地后结构撤销只到 28.9ms：查出来是「账被扔了」——加节点后当前代的**内容指纹**变了（含结构），
它进不了候选；`put_memo` 又只把「没用上的候选」退成上一代，于是「改之前」那份账当场被丢，
下一步撤销时手里已经没有能对上的账，只好再付一次全量。

改法一行成句：候选只挑「指纹对得上」的那几代，**对不上的留在手里**——
没有别的可留时，就把最近的那代（哪怕这轮指纹对不上）退成上一代。
它记着的正是另一个真实存在过的内容状态，撤销退回去时正好用上。

| 指标 | 第一步 | 第二步 |
| --- | --- | --- |
| 20k 结构撤销重建（缓存路径） | 28.9 / p95 31.1 | **中位 15.8 / p95 17.1** |
| 20k 文字撤销 / 重做 | 15.7 / 15.3 | 15.5 / 15.4（持平） |
| 20k 改字重建（缓存） | 15.9 | 15.9（持平） |

新增单测 `a_structural_undo_reuses_the_previous_generation`（加一颗 → 重建 → 撤销 → 重建，
断言行数据与加之前是同一份 `Arc`）；第一步的实现正是让这条测试红的形态，改完即绿。
