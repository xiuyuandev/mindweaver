# M12c · 20k 真增量重建（打磨轮 11）

> 依据：`docs/x100/polish-ledger.md` §3 第 7 条后半「20k 真增量布局」；预算 `docs/08` §2 P7（改 1 节点 ≤ 16ms）。
> 前作：`shots/x100/M12b/report.md`（分阶段账：20k 缓存路径 29.0ms，其中 `resolve_all` 5.5 +
> `measure` 5.7 这两段**与「改了什么」无关**）。
> 状态：`已实现`。20k 打字重建（缓存路径）**29.0 → 18.6ms**（含 `Command::SetText` 的端到端），
> 场景内部（P7 的「布局函数计时」口径）**p50 15.5 / p95 16.9ms**——P7 的 16ms **p95 仍差 0.9ms，未完全达标**。

## 1. 这一轮要解决什么

M12b 的账说明：20k 一轮重建 **25ms 是骨架价**，测量缓存 100% 命中也要付——每个节点每轮都要
「查样式表 → 查测量缓存 → 组装盒子 → 组装 `SceneNode`」。其中有两段是**纯浪费**：

| 段 | 中位 | 改一个字时它变了吗 |
| --- | --- | --- |
| `resolve_all` | 5.5ms | **不变**：样式级联只依赖主题 + 每个节点的覆盖样式 + 树形，不依赖文字 |
| `measure`（缓存命中的那部分） | 5.7ms | **不变**：20k 个盒子里只有正在编辑的那一颗换了文字 |

把它们每轮重算一遍，就是 P7 过不了线的直接原因。

## 2. 非目标

- 不改视觉、不改 `Command`、不改 `.zmind`、不加依赖。
- **不做**「把上一份 `Scene` 拿回来原地改」那种 API 级改造（`build_scene_cached` 仍然返回新 `Scene`）：
  骨架里剩下的 `nodes`（6.9ms）与 `collect`（2.6ms）这轮先不动，先把纯浪费的两段拿掉。
- 不覆盖卡片页 / 大纲的 20k 路径（不同渲染管线）。

## 3. 设计：`SceneCache` 里留一份「上一次的账」

`SceneCache` 目前只缓存盒子。这一轮再加一份 `RebuildMemo`：

```text
ids / depth / parent     前序表（结构是否变了，逐项比对，不散列）
style_in                 每个节点的覆盖样式输入（Option<StyleOverride>）
texts                    每个节点上次用到的文字（含「编辑中的那一颗」的入参文字）
styles                   每个节点上次解出的 ResolvedStyle（与 ids 对齐的 Vec）
boxes                    每个节点上次的 NodeBox（含 Arc 行数据，clone 只加引用计数）
theme / settings / root  主题、布局设置、布局根
```

一轮重建的判定顺序：

1. 前序走一遍（这步本来就要做，`collect` 2.6ms 不变），得到新的 `ids/depth/parent`。
2. 与 memo 逐项比：**结构没变**（同一批 id、同样深度与父）且 `theme`/`settings`/`root` 相同 →
   继续；否则整份作废，走原来的全量路。
3. 逐节点比 `style_in`：全等 → 直接用 memo 的 `styles`，**不跑 `resolve_all`**。
4. 逐节点比 `texts`：相同 → 直接用 memo 的 `boxes[i]`；不同（通常就一颗）→ 正常走测量缓存。
5. `bands/place/bounds/edges` 照旧重算——它们本来就只花 1–2ms，且位置确实会变。

不变量：memo 只是**加速**，任何一项对不上就整份丢掉重算，所以「算错」的最坏后果是慢，不是画错。
这条要靠金样兜底（146 场零漂移是硬门槛）。

## 4. 量法

- `perf_scene` 的「改字重建(缓存)」就是这条路径（同一份 `SceneCache` 反复重建），不需要新语料。
- `MW_LAYOUT_LOG=1` 看分阶段：缓存路径现在打 `reused=19999`（两万颗里只有改字的那颗重新测量），
  `[scene]` 的 `resolve` 从 5.5 降到 3.0（剩的是内容指纹本身），`nodes` 从 7.5 降到 1.5（场景节点整表克隆）。
- 两条口径都记：P7 的判据写的是「布局函数计时」，对应 `[scene] total`；终端用户感受到的是
  「命令入栈 + 重建」的端到端，即 `perf_scene` 报的数字。后者比前者多 2–3ms。
- 反例由单测把关：结构一变（加子节点）账整份作废、加备注必须重新装配那颗节点、
  同一份文档连画两遍每颗节点的行数据都是同一份 `Arc`。

## 5. 实测（同机 release；改字取 40 次取中位/p95）

| 指标 | M12b（改前） | 本轮 | 判据 |
| --- | --- | --- | --- |
| 20k 改字重建（缓存路径，端到端） | 29.0ms（p95 30.3） | **18.6ms**（p95 20.4） | P7 16ms ❌ |
| 20k 场景内部 `[scene] total`（P7 口径） | ~25ms | **p50 15.5 / p95 16.9 / min 13.4** | p95 16ms ❌（差 0.9） |
| 5k 改字重建（缓存路径） | 4.7ms | **3.5ms** | ✅ |
| 500 / 2000 缓存路径 | 0.3 / 1.3ms | **0.3 / 1.3ms**（持平） | ✅ |
| 20k 全量 `build_scene`（冷缓存） | 39.0ms | 39–49ms（机器噪声内持平） | — |
| 分阶段（缓存路径） | resolve 5.5 / measure 5.4 / nodes 7.5 | **resolve 3.0（内容指纹） / measure 2.3 / nodes 1.5**，`reused=19999` | — |

数字解读：省下来的 10ms = 样式表（5.5）+ 测量查表（5.4）+ 场节点装配（7.5）− 内容指纹（3.0）
− 克隆账本与场景表（约 2）。剩下的账（collect 3.0 / index 1.2 / order 1.1 / bounds 1.2）都是
O(n) 的结构性重建，要再往下就得连 `ids` / `index` 一起 `Arc` 化——那是 API 级改动，另立一行。

## 6. 单测（新增三条）

1. `the_scene_memo_rebuilds_a_node_whose_flags_changed` — 给节点加备注必须让下一轮重新装配它
   （这条**当场抓到真 bug**：第一版指纹没覆盖备注/链接/卡片，备注点了画布上看不见）。
2. `a_structure_change_drops_the_layout_memo` — 加一颗子节点后账整份作废，新节点进场景。
3. `painting_the_same_document_twice_reuses_every_box` — 同一份文档连画两遍，每颗节点的行数据
   都是同一份 `Arc`。另有一条旧单测 `the_box_cache_remeasures_only_when_a_size_input_changes`
   当场抓住第二版指纹漏了图标——改图标仍命中旧盒子，把宽度画错。

## 7. 未做 / 风险

1. **P7 的 16ms 只到 p50**（15.5），p95 16.9 还差 0.9ms。下一刀在 `collect`（3.0ms：20k 次
   id 克隆）与 `index`（1.2ms：20k 次 id 克隆进表）——都要把 `Scene::ids` / `Scene::index`
   改成 `Arc` 才能复用，是 API 级改动，单独记账。
2. 指纹是概率判据：结构指纹 2^-64 碰撞理论上可能「复用了错误几何」。已用节点数 + 深度数组
   双重闸门压低，且后果是画错而非崩溃；金样 146 场零漂移是硬背书。
3. 概念图不走复用（默认样式取决于图结构，指纹没覆盖那一层）——概念图节点数远小于 20k，可以接受。
4. 内容指纹每轮要再走一遍树（3.0ms）：与它省下的 `resolve_all` 5.5ms 相比是净赚，
   但这一段本身没有可复用的账——要消掉得和 collect 合并成一次遍历。
5. 20k 首次打开仍是全量（43ms，P3/P4 预算内）；撤销/重做仍是全量（41ms，P9 30ms 超预算）——
   它们改的是结构，本来就不该吃这份账。
6. 实机手感（20k 文档连续打字的帧率）没量过：离屏 harness 只有重建耗时，没有真实帧间隔。
