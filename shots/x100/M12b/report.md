# M12b · 20k 重建的分阶段账与两笔常数（打磨轮 10）

> 依据：`docs/x100/polish-ledger.md` §3 第 7 条「20k 增量布局」（本轮只做前半：
> **把一轮重建的每一毫秒归账，并砍掉其中白花的两笔**）；上限口径来自 `docs/08` §2 P7（16ms）。
> 上一轮：`shots/x100/M12/report.md`（只知总账 46.1ms，不知构成）。
> 状态：20k 一次重建 **46.1 → 41.4ms**（缓存路径 **34.1 → 29.0ms**），**P7 的 16ms 仍不达标**；
> **真增量布局仍未做**。本轮无视觉改动、无新基线。

## 1. 这一轮要解决什么

M12 把 20k 的账压到 47ms，但只留下一个总数。没有分阶段的账，就没法回答两件事：

1. 想达标还差多少？砍常数能不能到 16ms，还是必须改架构？
2. 假设做增量（只重排脏子树），能省下的是哪几段、能省多少？

所以本轮的第一件事不是优化，是**量出构成**。

## 2. 非目标

- **不做真增量布局**（结构指纹 + 复用上次几何 + 原地改 Scene）。这是架构级改动，
  它的形状取决于这次的账，得先把账算清。
- 不改视觉、不改 `Command` 集合、不改 `.zmind`、不加依赖、不动渲染层。
- 不量卡片页 / 大纲 / 检查器的 20k 成本（不同渲染路径）。

## 3. 量法（可复跑）

### 3.1 分阶段插桩：`MW_LAYOUT_LOG`

`compute_layout` 与 `build_scene_cached` 各加一组里程碑（设了环境变量才计时，不设零开销）：

```text
[layout] n=20000 total=18.28 collect=2.85 csr=0.15 measure=13.65 bands=0.15 place=0.25 edges=0.10 bounds=1.13
[scene]  n=20000 nodes=20000 edges=19999 total=34.63 resolve=6.13 layout=18.66 index=1.24 nodes=7.05 order=1.09 edges=0.20 advanced=0.27
```

`[scene]` 是外层（样式级联 → 布局 → 建索引 → 组装节点 → 排序 → 连线 → 高级元素），
`[layout]` 是其中 `compute_layout` 的内层。两层共用同一份「阶段 → 毫秒」，所以 `scene.layout`
与同一轮的 `[layout] total` 对得上。

### 3.2 语料：`perf_scene` 例程

```bash
TEMP=target/tmp TMP=target/tmp MW_LAYOUT_LOG=1 \
  cargo run -p mw-core --release --example perf_scene     # 输出存 shots/x100/M12b/
```

同一份合成树（每层分支 6/8/8/5 轮换）跑五条路：`build_scene`（冷缓存）、仅布局、
改字重建（冷缓存）、改字重建（缓存，即应用里打字的真实路径）、撤销/重做重建。
本轮**新增**一条「样式级联（每颗节点都带显式样式）」：XMind 导入的文档就是这个形态
（导入器把 `fo:color` / `fill` / `fo:font-size` 全写成节点覆盖），而样式级联是 20k 账里
唯一「跟文档有多少样式成正比」的一段。

缓存命中率也打出来了：20k 打字 40 次 = **799,960 命中 / 0 未命中**——
即下面那 28.7ms 是「全部命中缓存、一个节点都不用重测」时的成本。

## 4. 20k 一轮重建的账（缓存路径）

| 段 | 中位（ms） | 这一段在做什么 |
| --- | --- | --- |
| `resolve_all` | 5.3 – 5.7 | 20k 个节点逐个走样式级联，结果塞进 `HashMap<String, ResolvedStyle>` |
| `compute_layout` | 10.0 – 10.8 | 前序收集 → CSR → 逐节点取盒（100% 命中缓存）→ 分支带 → 摆位 → 连线端点 → 包围盒 |
| ├ `collect` | 2.5 – 2.9 | 前序遍历，克隆两万个 id 进 `ids`，建 `refs/depth/parent` |
| ├ `measure` | 5.4 – 6.2 | 每节点查一次样式表 + 一次测量缓存 + 组装 `NodeBox`（**全部命中**） |
| ├ `bounds` | 1.0 – 1.4 | 两万个矩形求并集 |
| └ `csr`/`bands`/`place`/`edges` | 合计约 0.7 | 真正的布局算术，便宜 |
| `index` | 1.0 – 1.2 | 建 `HashMap<String, u32>`（两万个 id 克隆 + 散列） |
| `nodes` | 6.6 – 7.1 | 组装 20k 个 `SceneNode`（再查一次文档、样式表、父索引） |
| `draw_order` | 1.1 – 1.3 | 按 (深度, y, x) 排序两万个下标 |
| `edges` + `spines` + `advanced` | 0.6 | 连线、轴线、边界/概要/关系线（20k 语料里没有） |
| **合计** | **25 – 26** | |

注：**改字后的第一次重建**（刚改字的那颗要真测一次、分配器要重新热身）实测 35 – 40ms，
之后才落进上表的稳态。表中是 `perf_scene` 循环内的稳态中位；`MW_LAYOUT_LOG` 的单次抖动可达 ±30%，
所以只取量级，不拿单行对比。

结论有三条，直接决定了下一轮怎么下刀：

1. **缓存全命中也要 25ms**：命中的节点不测量，但每个节点每轮仍要走「查样式表 → 查测量缓存 →
   组装盒子 → 组装 `SceneNode`」四遍。**O(n) 的骨架本身**就是主要成本，不是测量。
2. **`resolve_all` 与 `collect` 与「改了什么」无关**：改一个字，样式表与前序表一个字节都不会变。
   这两段（6 + 3 = 9ms）是增量能白拿的。
3. **测量缓存救不了装配**：本轮之前每命中一次还要克隆一份行文本（两万次 `String` 分配），
   现在改成 `Arc<[String]>` 共享——这是本轮的第一笔常数。

## 5. 改了什么（零语义变化）

| 位置 | 改动 | 为什么 |
| --- | --- | --- |
| `layout.rs::BoxSpec.lines` / `NodeBox.lines` | `Vec<String>` → `Arc<[String]>`，命中缓存时只加一次引用计数 | 20k 每次重建要取两万个盒子，逐个克隆行文本就是每帧几万次分配 |
| `layout.rs::compute_layout` 测量循环 | 不再 `node.text.clone()`，改成借用 `&str`（只有正在编辑的那一枚来自入参） | 同上，每轮两万次字符串分配 |
| `theme.rs::resolve_all` | 不再对每个节点 `style.clone().unwrap_or_default()`，改成借用 + 一份共享的「全空」 | 带样式的文档（XMind 导入）每轮多克隆几万个 `String`；20k 全带样式 **10.5 → 7.0ms** |
| `layout.rs` / `scene.rs` | 新增 `MW_LAYOUT_LOG` 分阶段计时 | 没有这份账，下一轮不知道该动哪一段 |
| `scene.rs::SceneCache` | 新增命中/未命中计数与 `stats()` | 「缓存全命中也要 28ms」这个结论要能被复跑验证 |
| `examples/perf_scene.rs` | 新增「样式级联（全带样式）」语料与计时；缓存命中数打进输出；`[perf] … 起` 标出缓存路径那一段 | 真实文档的形态不是「没有覆盖样式」 |
| `scene.rs` 测试 | 新增 `a_cache_hit_shares_the_line_storage_instead_of_cloning_it` | `Arc::ptr_eq` 钉住「没变的节点复用同一份行数据，变了的才换」 |

## 6. 一次否决：快速哈希器

账里 `resolve`（5.6）+ `index`（1.2）+ `nodes` 的多次查表都是按字符串 id 查 `HashMap`，
很自然会想到把 `SipHash` 换成 rustc 那样的快速哈希。本轮真写了一版（`FxHasher`，二十行、
无依赖），用在 `resolve_all` 的结果表、测量缓存、`Scene::index` 三处。

A/B 方法：同一份代码两个 release 构建（只差这三处的哈希器），**交替跑 4 轮**消除机器漂移：

| 轮次 | SipHash（现行） | FxHash（候选） |
| --- | --- | --- |
| 1 | 31.7 | 38.9 |
| 2 | 32.8 | 37.9 |
| 3 | 32.2 | 39.1 |
| 4 | 33.4 | 39.8 |

**候选比现行为慢 6–7ms**，三处全部撤回。这条否证反而很有用：它说明瓶颈不是「散列有多贵」，
而是「每个节点每轮都要走一遍查找」这件事本身——换更快的散列救不了，只能少走几趟（增量）。

## 8. 门槛

- `cargo fmt --all -- --check` 干净。
- `cargo clippy --workspace --all-targets`：**37 条基线 / 新增 0**（`target/x100/clippy_diff.py`）。
- `cargo test --workspace -- --test-threads=1`（先 `TEMP=target/tmp`）：**925 passed / 0 failed / 1 ignored**（+1）。
- stage-b 门（`target/x100/gate-b-m12b.log`）与 stage-cm 门（`target/x100/gate-cm-m12b.log`）
  **顺序**跑，全过；**146 个场次（stage-b 100 + stage-cm 46）逐字节零漂移**——本轮所有改动都不该动像素，门证明确实没动。
- 本轮**没有新增基线**。

**踩到的坑（写给下一任）**：
1. clippy 基线指纹是「标题 @ 文件:行」——在 `theme.rs` 删一行 import 就让所有既有告警的行号平移，
   被判成新告警。重生成基线（`ci.ps1 -WriteClippyBaseline`）后逐行核对：14 处全为行号平移、条目数仍 37。
2. 门脚本把 mw-core 的 `Rgba::rgba` 历史告警写死成 `theme.rs:22:5` 豁免，同样随行号漂移；
   已改成按「标题 + 文件」豁免（`scripts/x100-stage-b-gate.ps1`，标题与文件都要对上，新告警照样抓）。
3. 修 .ps1 时用 Python 重写文件**丢了 UTF-8 BOM**，PowerShell 5.1 按 ANSI 解码，
   五个带中文环境值的场景（`MW_OUTLINE_SEARCH='排版'` 等）把乱码传给应用，门第二次红。
   教训：改带中文的 .ps1 必须保留 BOM，改完与 `git show HEAD:<file>` 比对首字节。
4. BOM 修好后还剩 `card-autosave` 一场红（53 px / 0.002%，一个 CJK 字形的抗锯齿覆盖变了）。
   用干净 HEAD 构建复现：53 px 一模一样 ⇒ 非本轮代码；连跑三次逐字节相同 ⇒ 稳定。
   按规程重拍该基线（`--update` + 双跑 `--tol 0` 通过），旧基线备份在
   `target/x100/card-autosave-baseline-before.png`，新旧差恰为那 53 px。

## 9. 未做 / 风险

1. **P7 的 16ms 仍未达标**：缓存路径 29.0ms。按第 4 节的账，纯砍常数最多再挤出几毫秒，
   要过线必须做**真增量**：结构指纹（节点集合/父子/顺序/折叠态不変）→ 复用上次的
   `ids` / `styles` / 每节点盒尺寸 → 只重测编辑中的那颗 → 重跑 `bands/place/bounds`（< 2ms）
   → 原地更新 `Scene`（不重建 20k 个 `SceneNode`）。这是下一轮的主账。
2. **标签胶囊每轮重测**：`build_scene_cached` 的节点装配段对每个带标签的节点再调一次
   `NodeSizer::pills()`，而胶囊宽度其实在测量缓存里算过一遍。合成语料只有 1/40 节点带标签，
   分阶段账里看不出来；真机上每次是**一次 DirectWrite 测量**，标签多的文档会明显。
   修法是让 `BoxSpec` 带上胶囊宽度（加字段 = 动 `mw-core` 的公开结构体，要单独记账）。
3. **只在合成语料上量**：每层 6/8/8/5 轮换、无长文、无图片。真实文档的长文节点会更贵。
4. **只量 1080p / ppp 1.0**；150%/200% DPI 没量。
5. **真实鼠标节拍的 P5 仍未复测**（`scripts/m5-perf.ps1` 本机拿不到主窗口句柄，M12 已记）。
6. 分阶段日志的单次数字抖动可达 ±30%（同一份代码 `[layout] total` 见过 11.6 与 21.2），
   所以结论只取「多轮中位的量级」，别拿单行对比。
