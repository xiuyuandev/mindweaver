## 0. 一页结论

层级样式**不是没有**：中心/一级/二级/三级的字号、行高、内距、填充、描边、分支线宽在四套主题下
**都能查到确定的取值**，且「填充/描边随分支色淡染」这条派生链是完整的（`mix 0.07` / `mix 0.22` /
`mix 0.20`）。问题集中在**四个面**：

1. **「按主题校准」这条路只覆盖颜色**：字号、字重、行高、内距、圆角、形状、间距**不是主题级令牌**
   （走全局常量或文档级设置），换主题只换色 —— 与「主题默认值」这个说法不符（G-25-01）。
2. **合同表还剩三处没对齐**：`docs/06` §2.2 仍写 28/20/15/14、内距 18×9、色板「与 `core/theme.rs`
   的 snow 主题一致」；代码是 28/20/**16**/**15**、内距按字号分四档、色板逐值不同（最大通道差 **62/255**）
   （G-25-02 / G-25-03 / G-25-05）。线宽那一行**已按 2026-11-02 口径改成「历史值，以代码为准」**，
   本包不重开。
3. **派生链有一个断口**：文档级强调色覆盖（`meta.theme_accent`）只旋转
   `ui.accent / accent_soft / palette / palette_fill`，**不旋转 `levels`** ——
   改完强调色会得到「蓝色分支线 + 绿色中心卡 + 旧色系描边」（G-25-06）。
4. **概念图与思维导图是两套默认值，没有对照表**：14/15 + 面板底 + 椭圆 vs 28/20/16/15 + 层级填充 +
   圆角，且概念图字号是 `theme.rs` 里的**局部常量**、比思维导图最深层（15）还小 1px（G-25-07）。

**会改可见外观的差距：2 条（G-25-03 收细三级内距 / G-25-07 抬概念图字号，都要拍板才动）；
影响 71 场 stage-b 场景（142 次比较）+ 80 场概念图（stage-b 7 + stage-cm 73）**。
其余 8 条是文档/令牌结构动作，**0 重拍**。**需拍板的项：3 条**（§3 末尾）。

### 2.1 层级 × 属性（四主题**共用**的部分）

| 层级 | 字号令牌 | 字重 | 行高（倍数 → 取整值） | 内距 `(pad_x,pad_y)` | 单行盒高 | 出处（字面） |
| --- | --- | --- | --- | --- | --- | --- |
| 中心主题（depth 0） | 28（`CANVAS_CENTER`） | **600**（`bold: true` → `weight = WEIGHT_BOLD_ALIAS`） | ×1.4 → 39 | (26, 12) | 63 | `crates/mw-core/src/theme.rs` `pub const LEVEL_TYPE: [(f32, bool); 4] = [` 第 1 项 `(crate::design::text::CANVAS_CENTER, true),` |
| 一级主题（depth 1） | 20（`CANVAS_MAIN`） | 400 | ×1.44 → 29 | (18, 10) | 49 | 同上第 2 项 `(crate::design::text::CANVAS_MAIN, false),`；`docs/06` §2.1「一级 ⋯ 黑字常规」 |
| 二级主题（depth 2） | **16**（`CANVAS_SUB`） | 400 | ×1.44 → 23 | (14, 8) | 39 | 同上第 3 项 `(crate::design::text::CANVAS_SUB, false),` |
| 三级及更深（depth ≥3） | **15**（`CANVAS_LEAF`） | 400 | ×1.46 → 22 | **(14, 8)**（与二级同档） | 38 | 同上第 4 项 `(crate::design::text::CANVAS_LEAF, false),`；`Theme::level()` 的 `len => self.levels[d.min(len - 1)]` 让 depth≥4 全部回落到这一档 |

三条配套公式（都只有一处出口）：

- 行高：`crates/mw-core/src/design.rs` `pub const fn line_height(size: f32) -> f32 {` ——
  `size <= 12.0 → 1.5`、`<= 15.0 → 1.46`、`<= 21.0 → 1.44`、其余 `1.4`。
- 内距：`crates/mw-core/src/design.rs` `pub const fn card_padding(font_size: f32) -> (f32, f32) {` ——
  `>= 26.0 → (26.0, 12.0)`、`>= 19.0 → (18.0, 10.0)`、`>= 14.5 → (14.0, 8.0)`、其余 `(12.0, 7.0)`。
  ⇒ **15 也落在 `>= 14.5` 这一档**，所以二级与三级的内距完全相同（层级只靠 1px 字号与 1px 盒高区分）。
- 盒高：`crates/mw-core/src/scene.rs` `fn text_height(lines: usize, line_h: f32, pad_y: f32) -> f32 {`
  —— `(lines as f32 * line_h + 2.0 * pad_y).max(32.0)`。

> **与 X22 §7.1 的一处不一致（如实记）**：X22 那张表给最深层的单行盒高是 **36**，按
> `card_padding(15) = (14,8)` + `line_height(15)=1.46` 复算应是 **38**（22 + 2×8）。
> 本包按源码字面记 **38**，并把差异列为待核（§6 R-3）——本轮不跑 `cargo`，不能实测裁定。

三个开关的实际含义（都在 `crates/mw-core/src/theme.rs`，`Theme` 字段注释里写明）：

- `branch_text: false` ⇒ 一级文字**不取分支色**，取 `levels[1].text`（与 `docs/06` §2.1「一级 ⋯ 黑字常规」一致）。
  `crates/mw-core/src/theme.rs` 里那句 `if depth == 1 && theme.branch_text && own_text.is_none() …` 因此恒不成立
  ——四主题都没走这条分支（字段存在但**当前无一处为 true**）。
- `main_card: true` ⇒ 一级按 `palette_fill_at(兄弟序号)` 上实色卡（`docs/06` §2.1 的「实色马卡龙填充」）。
- `taper: true` ⇒ 分支线逐边收细；线宽公式见 §2.3。

### 2.3 派生规则：哪些值是算出来的

| 输入（令牌或文档字段） | 派生公式（字面） | 谁受影响 |
| --- | --- | --- |
| `design::text::CANVAS_*`（28/20/16/15） | `LEVEL_TYPE` → `levels[i].font_size` → `card_padding` 分档 → `text_height` → 盒宽高 → 布局 | **全部四个层级** + 所有画布基线 |
| `Theme::palette[i]`（兄弟序号取模） | 分支色：根 = `ui.accent`；一级 = `palette_at(兄弟序号)`；子孙继承父链；显式 `StyleOverride.branch_color` 优先 | 一级及以下的**填充、描边、分支线色**三样 |
| `Theme::palette_fill[i]` | 一级卡片填充（未显式指定分支色时） | 一级卡片 |
| 一级填充 | 描边 `level_fill.mix(branch, 0.22)`（`crates/mw-core/src/theme.rs` 的 `level_fill.mix(branch, 0.22)` 那行） | 一级描边（**`levels[1].stroke` 因此形同虚设**） |
| `levels[i].fill`（i ≥ 2） | 填充 `level.fill.mix(branch, 0.07)`、描边 `level.stroke.mix(branch, 0.20)` | 二 / 三级（示例：snow 二级 `#FDFCF9` × `#3A7D6C` ⇒ 填充 `#EFF3EF`、描边 `#CBD4CA`） |
| 显式分支色 | `Theme::branch_fill`：`Rgba::rgb(0xff,0xff,0xff).mix(branch, 0.5)`（亮）/ `self.ui.panel.mix(branch, 0.2)`（暗） | 该分支的一级卡片 |
| `edge_width_root` / `edge_width` | `edge_width_at`：depth0 = root、1 = root×0.75、2 = edge_width、≥3 = `(edge_width * 0.75).max(1.0)` | 四档线宽（§2.4） |
| `ui.accent` | 根出发线色；概念图主概念 8% 强调底；`with_accent` 时**旋转** accent / accent_soft / palette / palette_fill | 分支线 + 一级卡片（**但不含 `levels`**，见 G-25-06） |
| `legible(theme)` | 若某支 palette 对画布或一级卡 `< 3:1`、或某层文字对底色 `< 4.5:1`，按 `×0.93` / `×0.9` 逐步压暗（最多 24 次，色相不变） | 色板 + 层级填充/文字 |
| 文档级 `theme_overrides` | `level1_fill` **同时**把整个 `palette_fill` 刷成一个颜色；`text` 刷全部层；`text_sub` 刷第 2 档及以后；`edge_scale` **同时**乘两个线宽（`clamp(0.4, 2.5)`） | 层级越多连带越广：一处覆盖能改 4 层 + 8 支 |

**`legible()` 今天是空操作（实测手算）**：把四主题的 `palette` 与四层文字按 WCAG 算了一遍
（画布底色 / 一级卡底色为准）——最低的是 **snow 的 `#B98A3E` 对画布 3.00:1**（正好踩在门槛上），
其余全部合规；四层文字最低 5.84:1。⇒ 源码字面 = 运行时值。
**但这条一旦被碰到就会「改一改多」**：把 snow 的赭石调亮 1% 就会跌破 3:1，`legible` 开始压暗，
验收时看到的就不是你改的那个值。

### 2.7 令牌结构（`Theme` 有几个族、命名是否统一）

`crates/mw-core/src/theme.rs` 的 `pub struct Theme {` 一共 **6 族**：

| 族 | 内容 | 备注 |
| --- | --- | --- |
| `ui: ThemeUi` | 13 个槽位：`bg / panel / panel2 / text / dim / border / accent / accent_soft / hover / canvas_bg / dot / dot_spacing / dot_radius` | 唯一「成套」的令牌族，注释明确「三处派生只能读 `canvas_dots()`」 |
| `palette: Vec<Rgba>` | 分支色循环表（8 / 6 / 6 / 6 / 1 支） | 长度不齐（G-25-05） |
| `palette_fill: Vec<Rgba>` | 一级卡实色（与 `palette` 手工配对） | 两表要人工同步，改一支就要改另一支 |
| `levels: Vec<LevelStyle>` | 4 项 × 7 字段（`fill / text / font_size / bold / shape / stroke / stroke_width`） | `font_size`、`bold` 四主题全填同一常量（等于「字段在但不可主题化」，G-25-01）；`stroke` 在 1/2/3 级被派生覆盖（§2.3） |
| 三个开关 | `branch_text / main_card / taper` | `branch_text` 四主题皆 `false`（等于死字段） |
| 两个线宽 | `edge_width / edge_width_root` | 命名不对称：`edge_width` 是「二级档」，`edge_width_root` 是「根出发档」，没有 `edge_width_l1/l3`（另两档是算出来的） |

命名/收敛上的四个具体问题（都不改外观，只记账）：

1. **字阶不在 `Theme` 里**：`LEVEL_TYPE` 是 `theme.rs` 的模块常量，引用 `design::text::CANVAS_*`；
   所以「主题」改不了字号（G-25-01）。
2. **内距不在 `Theme` 里**：`design::card_padding(font_size)` 按字号分档——主题改不了内距。
3. **圆角不在 `Theme` 里**：`NODE_RADIUS` 在 `mw-render`，`LevelStyle` 没有 `radius` 字段（SE-13 只做到
   节点级 `ResolvedStyle.radius` 覆盖）。
4. **`Theme::level()` 的兜底又抄了一份默认值**：层表为空时用 `fill: self.ui.panel, text: self.ui.text,
   font_size: LEVEL_TYPE[3].0, bold: LEVEL_TYPE[3].1, shape: Shape::Rounded, stroke: self.ui.border,
   stroke_width: 1.0` —— 同一套默认值在仓库里出现第二处，改档位容易漏（G-25-09）。

## 3. 差距清单

格式：**现状 → 合同/参考值 → 影响面 → 要不要动令牌或数据模型**。凡是「照合同改就会改可见外观」的
条目额外标注 **需重拍基线** 与受影响基线名。基线名取自 `scripts/x100-stage-b-gate.ps1` 的场景表
（178 场）与 `scripts/x100-stage-cm-gate.ps1` 的场景表（73 场），族计数见 §5.3。

### 3.1 结构类（不改外观）

**G-25-01 · 主题默认值只覆盖颜色，层级样式不是主题级令牌**（**含 X23 委托来的三条**）
现状：字号 `LEVEL_TYPE`、内距 `card_padding`、行高 `line_height`、圆角 `NODE_RADIUS` 都是全局常量，
`Theme` 只有 `levels[].fill/text/stroke/shape` 可动；间距在 `LayoutSettings`（文档级）。
X23 裁决「其余**令牌类推后到 X25 一起收**」的三条也落在这里：
① **G-5「令牌三套语言」**——`design::text`（画布）、`design::ui`（壳层）、`design::content`（内容面）
三套字阶 + 画布层级的第四种映射（`LEVEL_TYPE`），四者之间只有文档约定、没有结构约束；
② **G-4「边框色是派生非令牌」**——一级描边 `mix(branch,0.22)`、二三级 `mix(branch,0.20)`
都是算出来的，`levels[i].stroke` 只在 `depth == 0` 与无卡主题下才真被用上（§2.3）；
③ **G-6「圆角上限与盒高耦合」**——`radius` 覆盖夹在 `0..=24`，而 `corner_style` 还要再按盒高
取 `min(w,h)/2`，两者没有一处统一出口。
→ 合同/意图：`docs/24` X25 要求「按主题校准层级样式」，`docs/35` 把 `design::text` 定为 primitive 层
（「原地保留、不改值」）。→ 影响面：**「换个主题，层级只变色」是设计选择还是缺令牌**，必须先裁；
三套语言要不要收敛成「一轨 + 派生」也要裁。→ 动令牌：是（`Theme` 结构内加 `level_pad` /
`level_radius` / 主题级字阶映射），**不动 `.zmind`**，不重拍。

**G-25-08 · `LevelStyle.bold: bool` 表达不了 500**
现状：层级默认字重只有 `bool`（true → `weight = WEIGHT_BOLD_ALIAS = 600`，false → 400）；
`design::text::WEIGHT_MEDIUM = 500` 在层级默认值里**没有出口**（只有节点覆盖 `StyleOverride.weight` 有）。
→ 合同：`docs/28` §4.1「只用 400 / 500 / 600 三档」。→ 影响面：若要让「一级 500」成为主题默认值，
必须把 `LevelStyle.bold` 扩成 `weight: u16`（`ResolvedStyle.weight` 已经是 u16，层这一侧还是 bool）。
→ 动令牌：是；值不变则**不重拍**。

**G-25-09 · 主题默认值没有单一出口**
现状：`snow()/ink()/mist()/sand()` 各手写 `levels` 4×7 + `palette` + `palette_fill`；`Theme::level()`
兜底再抄一份；`legible()` 会在运行时改写色板与层级文字（§2.3）。
→ 参考：`docs/35` T1「抽令牌」工单（要求逐像素 0 差异）。→ 影响面：改档位要改 4 处 + 1 处兜底。
→ 动令牌：是（纯重构）；**不重拍**（验收口径：`--tol 0` 全零）。

### 3.2 取值类（照合同改就会改外观 ⇒ 需重拍）

**G-25-02 · 画布字阶 28/20/16/15 vs `docs/06` §2.2 的 28/20/15/14** ｜ **不重拍（建议按已裁口径改文档）**
现状：二级 16、三级 15（§2.1）。合同：`docs/06` §2.2「二级 15；更深 14」，且该表同段自述
「v8 对齐 XMind 2026 主题令牌」（即它本来是「参考」而不是「现值」）。
→ 权威口径：`docs/35` §0.1「取值仍以 `mw_core::design` 的实现为准」；同类事已有先例——
`decisions-2026-11-02-stage-c.md` §1 X22 **G03** 判「以 `design::content` 现值为准，改文档，
**不许**顺手改任何字号令牌」，理由是现值已进基线。⇒ 建议照同一口径：**改文档 + 改 `theme.rs`
