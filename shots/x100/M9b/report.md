# M9b · 整图折叠与聚焦视图下的折叠圆点（打磨轮 67）

> 依据：`docs/x100/polish-ledger.md` §3 第 16 项（M9 行「已知粗糙」里那句
> 「整图折叠与聚焦模式下的圆点没拍」）。
> 状态：**已实现（机器门见 §4；实机手感仍 `未验证`）**。
> **本轮基本不改产品行为**——纯证据轮，只动了一行轨迹导出（§5，`MW_TRACE` 守卫内，不碰像素）。

## 1. 这一轮要解决什么

M9 的四张基线（`mm-collapse` / `mm-collapse-mid` / `mm-toggle-edge` / `mm-toggle-miss`）
拍的都是**默认展开态**下的单颗圆点：怎么折、折到一半长什么样、热区比画出来的环大多少、
差 3px 会不会误折。这些都成立。

没拍的是另外两种**整体状态**下的圆点：

| 状态 | 入口 | 该看到什么 | 本轮之前有没有证据 |
| --- | --- | --- | --- |
| 整图折叠 | `Ctrl+/` → `Command::SetCollapsedAll{collapsed:true}` | 可见的带下级节点全是「＋」 | 只有 document 层的单测 |
| 聚焦视图 | `Alt+Enter` / `MW_FOCUS_DEMO`（`focus_selected`，只改视图不改文档） | 聚焦边界上该露的圆点还在，视图外不留残点 | 只有 `search-focus-jump` 一张间接图 |

风险具体是两处：

1. `SetCollapsedAll` 之后相机走 `reveal_node`（只保证主选在屏内），圆点跟着节点移动——
   没人核对过「折完之后屏幕上看到的每一颗带下级的节点都是 ＋」。
2. 聚焦时 `Scene` 是裁剪重建的：如果裁剪把某层子级留进场景却折了父级，
   会出现「视图里有一颗打不开的圆点」这种自相矛盾的画面。

## 2. 非目标

- 不改 `SetCollapsedAll` / `focus_selected` 的语义，不改热区半径、圆点尺寸、过渡时长。
- 不动 `mm-collapse` 那四张既有基线（外观零改动，它们必须零漂移）。
- 不做实机手感（触控笔、150%/200% DPI）——M9 行那条缺口不在本轮口径里，仍 `未验证`。
- 不碰概念图（`cm-*`）与检查器。

## 3. 验收场景

两张新基线，都进 `stage-b` 门，`--tol 0` 连跑两次：

| 场景 | 夹具 | 输入脚本 | 钉住什么 |
| --- | --- | --- | --- |
| `mm-collapse-all-dots` | 默认样例（`MW_NOTES=none`） | 落定后 `key ctrl+/`，指针移开 | 整图折叠终态的圆点集合 |
| `mm-focus-dots` | `MW_DRILL_DEMO=纯 Rust 原生` + `MW_FOCUS_DEMO=纯 Rust 原生` | 落定后指针移开 | 聚焦视图**内部**的边界圆点 |

聚焦场景第二版才有效：第一版只 `MW_FOCUS_DEMO=中文排版`，拍出来三颗子级全是叶子，
**画面里一颗圆点都没有**——那只能证明「没有残点」，证不了「边界圆点还在」。
于是借第 66 轮的 `MW_DRILL_DEMO` 给「winit + windows-rs」挂一颗孙子「GPU 合成」，
再聚焦「纯 Rust 原生」，边界上就真的有一颗该画的圆点（§5 的轨迹对照）。

## 4. 实测

### 4.1 画面结论（逐张核对，不是「看着差不多」）

**整图折叠**（`shots/golden/mm-collapse-all-dots/shell-ppp1.00.png`，sha256 前 12 位 `ab78308c91d1`）
折叠后场景剩 5 个节点（根 + 4 颗一级），轨迹 `trace-collapse-all.txt` 终态的 `scene_toggle` 恰好 3 条：

| 节点 | 有下级？ | 圆点 |
| --- | --- | --- |
| 织思（根） | 是 | **不画**（根没有父级，见 §5） |
| 纯 Rust 原生 | 是 | ＋ |
| 中文排版 | 是 | ＋ |
| 交互与性能 | 是 | ＋ |
| 导出 | 否 | 不画（叶子本来就没有） |

即「可见的带下级节点全是 ＋」成立，没有第 2 节担心的那种「看得见却打不开」或「该有圆点却没有」。

**聚焦视图**（`shots/golden/mm-focus-dots/shell-ppp1.00.png`，sha256 前 12 位 `053b98ae6977`）
聚焦「纯 Rust 原生」后场景 4 个节点、`scene_toggle` **恰好 1 条**（`winit + windows-rs`，屏幕 (536,551)）：

- 聚焦根 `纯 Rust 原生` 不画圆点——裁剪后的场景里它没有父级，与整图折叠那张的根同一条判据；
- 边界上的 `winit + windows-rs`（有子级「GPU 合成」）圆点在，且是**展开态**的形态；
- 视图外的 `中文排版` / `交互与性能` 等一颗残点都没有；
- 左上角面包屑「织思 › 纯 Rust 原生」与圆点不重叠。

## 5. 顺带查出的一处轨迹不实（本轮唯一的代码改动）

对着画面核 `trace-collapse-all.txt` 时发现：终态轨迹列了 **4** 条 `scene_toggle`，
画面上只有 3 颗圆点——多出来的那条是**根主题**的。

原因在轨迹导出本身：`canvas_methods_2.rs` 的 dump 循环只按 `n.has_children` 判，
而真正的绘制与命中（`mw-render/src/hit.rs` 的 `if n.has_children` 里面还套了
`if let Some(parent) = n.parent…`）要求**有父级**。所以根被写进了「圆点清单」。

这不是画面 bug（根本来就不该有圆点，也确实没有），但它是**证据的 bug**：
以后谁拿这条轨迹去点根主题的「圆点」，就会像第 37 轮那三张点在空白处的坐标一样自欺。
改法是把 dump 的判据对齐 `HitMap`——没有父级就 `continue`。
改动在 `if crate::trace::is_enabled()` 块内，不设 `MW_TRACE` 时零路径，**不可能动像素**。

## 6. 顺手量到的一条事实（记给账本 §3 第 15 项）

跑完两场之后，用 `mm-drag-child.txt` 在 `--ppp 1.5` 下打了个探针（`probe-ppp150-trace.txt`），
想确认「150%/200% 条宽证据」是不是注册四张 `Ppp='1.5'` 就行。**不是**：

| 档 | 回读物理尺寸 | 落定 `fit` |
| --- | --- | --- |
| ppp 1.0 | 1620×1080 | `vp=1620x1006 zoom=1.3312` |
| ppp 1.5 | 1620×1080 | `vp=1080x646 zoom=0.8545` |

物理窗口尺寸固定，`ppp` 一变，**逻辑视口跟着缩**，整图 `fit` 的 zoom 从 1.3312 掉到 0.8545——
150% 档不是「同一张图更密的像素」，而是另一张布局。`mm-drag-child.txt` 的 (463,605) / (1027,631)
在 1.5 档落在空白，照抄注册只会拍到「按下没拖起来」（与第 37 轮那三张失效坐标同一个坑）。
所以那一条账的真实工作量是**每档各跑一次 `MW_TRACE`、从 `scene_node` 落定矩形重取源/目标中心**，
四张基线 = 四次量坐标。已把这条写进 `docs/x100/polish-ledger.md` §1 M5 行与 §3 第 15 项。
