## 2. 实现 · 保存管道

### 2.1 两阶段写盘

- 读者页：`is_dirty()` 且停手 ≥800ms → `mark_saving()`（顶栏这一帧画「保存中…」）→
  发 `ReaderAction::Save`。
- 壳层：把请求放进 `pending_card_save`（`CardSave { title, body, tags, close }`），
  **下一帧开头** `pump_card_save` 才写盘——与文档 `SavePhase::Saving` 同一套两阶段，
  「保存中…」说的才是真话；成功后 `mark_saved()`、失败 `mark_save_failed(msg)`。
- 顶栏：`只读` / `保存中…` / `保存失败` / `编辑中 · 稍后自动保存` / `已保存` 五态，
  状态字前固定一个 **6px 圆点**（与状态字同色）。
- 外观漂移：全部卡片场景多一个点。`card-reveal` 实测 **242 px（0.011%）**，
  包围盒正好是那个点（x[1639..1682] y[26..37]）；受影响的 30 张基线全部按
  `docs/29` §5 协议重拍并双跑 `--tol 0`。

### 2.2 失败路径与金样确定性

- `autosave_due(dirty, saving, idle_from, now, delay)`（纯函数）：
  脏、不在写、停手满 `delay` 三条都成立才发。正在写盘时**绝不**重排队——
  修掉了旧实现「失败后 `dirty_since` 不清 → 每帧重试一次写盘」的打磁盘循环。
- `mark_save_failed`：清掉计时（等下一次输入或 `Ctrl+S` 再试）、保留草稿、
  顶栏挂「保存失败」。
- **金样里默认关自动保存**：截图与真实时钟赛跑会让同一份构建拍出「有时已保存、
  有时还在编辑」两张图。要拍这一格，脚本显式给 `MW_CARD_AUTOSAVE=<ms>`
  （`card-autosave` 场景用 50ms + `sleep 200`，判定离边界很远）。

## 3. 实现 · 外部修改与只读

### 3.1 指纹

- 打开库内卡片时记下 `file_guard::fingerprint(path)`（长度 + 修改时间毫秒），
  写盘成功后刷新。
- 写盘前 `file_guard::changed_since(known, now)`：两边都有且不同 → 冲突。
  从没见过（新建）或现在读不到都不算——不吓唬正常的新建卡片。

### 3.2 冲突行内条

- 顶栏下方 32px 行内条（warn 10% 底 + 1px 描边，圆角 6）：「重新加载 / 覆盖 / 取消」三个
  小按钮 + 「文件已在外部修改」，**不拿模态遮正文**。
- `重新加载`：丢掉本页草稿，按磁盘内容重开（`reload_card_from_disk`）；
  `覆盖`：跳过指纹检查立刻按当前草稿写一次（`card_overwrite` 一次性旗标）；
  `取消`：这一笔不写，顶栏回到「编辑中」，下次自动保存仍会先比指纹。

### 3.3 只读

- 打开卡片时用「追加打开」探测可写性（不写内容）；不可写 → `set_read_only(true)`。
- 只读时：正文 `TextEdit::interactive(false)`（光标进不去，回车接管 / 粘贴 / 勾选那几条
  全部自然跳过——它们都以 `body_focused` 为前提）、任务框点击被忽略、自动保存不排队；
  `Ctrl+S` 由壳层提示「这张卡片只读：请另存为」。
- 实拍对照：只读 + 「点进正文敲字 + 回车」与静置只读**逐位相同（0 px）**，
  trace 里 0 条 `card_body`。

## 4. 实现 · 20k 长文性能（探针）

- 探针：`MW_CARD_PERF=<文件>` 时逐帧记录画卡片页的耗时（`trace::card_frame_ms`），
  第一行即打开成本（含 20k 字符排版）。
- 夹具 `MW_CARD_20K=1`：按 `chars < 20000` 生成中文正文的一张卡。
- 实测（1800×1200 @ ppp 1.0，release）：

| 场景 | 打开(首帧) | p50 | p95 | max | >50ms | >16ms |
| --- | --- | --- | --- | --- | --- | --- |
| 打开 20k（24 帧） | **5.5 ms** | 1.7 | — | 5.5 | 0 | 0 |
| 连续输入 200 字（432 帧） | 5.4 | 1.7 | 3.6 | 5.4 | **0** | 0 |
| IME 组合 20 轮（152 帧） | 5.4 | 1.7 | 3.4 | 4.4 | — | **0** |

合同判据全部达标（打开 ≤150ms、输入无 >50ms、IME ≤16ms）。
注意：IME 是构造事件（`ime preedit/commit`），不是真输入法——这条限制与 CER-16/17 相同。
首轮测量没有超预算，所以**没有**上块级缓存；`docs/28` §6.9 的块级缓存是手段不是门，
留作真实使用暴露瓶颈时再动。

## 6. 未做 / 风险

1. **只读探测的边界**：「追加打开」在独占锁定类失败上可靠，但网络盘/杀软瞬时占用
   会误报只读；下一帧不会自动恢复，需要重开卡片。
2. **外部修改只覆盖库内卡片**：文档内卡片存在 `.zmind` 里，走文档级冲突（模态），
   与合同的「行内条」不同——那是既有文档保存路径的设计，本轮不动。
3. **「保存中…」实际只亮一帧**：写盘很快；能拍出静态样子是因为夹具直接置位。
4. **20k 的 IME 是构造事件**；实机微软拼音仍未核对（CER-07 遗留，全员共用一个 IME 门）。
5. 20k 只在 1.0 DPI 拍基线；滚动帧率没单独量（golden 帧循环不是真实节拍，量了也不可信）。
