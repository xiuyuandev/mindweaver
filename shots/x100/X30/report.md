## 1. 门的范围与非目标

### 1.1 这个门要证什么

`docs/24` §3 阶段 C（X21–X30）重做的是「画布视觉与内容表达」：相机与缩放（X21）、DirectWrite 字阶与
CJK 混排（X22）、节点卡片与形状（X23）、分支线与箭头（X24）、层级样式与主题默认值（X25）、
画布角标（X26）、状态表（X27）、圆点/手柄（X28）、空态与错误态（X29）。这些包各自的证据是**分项**的；
X30 是**把它们放进同一批取景里、在四主题与三档 DPI 下一起看**的收口门——单项都对、合起来不成立
（浅主题细线发灰、200% 下铬件变粗、深树字阶塌成一片）是这一门唯一要抓的东西。

因此本门的产物是**一批统一取景的双跑基线 + 一张判词表**，不是新功能。

## 2. 矩阵设计

### 2.1 先定「维度能不能正交」

| 维度 | 取值 | 会对谁产生跨域影响 | 结论 |
| --- | --- | --- | --- |
| 主题 | `snow` / `ink` / `mist` / `sand` | 颜色、对比度、点阵纹理可见度；**与 DPI 强耦合**（浅主题的细线/角标在 200% 下最危险） | 与 DPI **全交叉** |
| DPI | `100% / 150% / 200%`（对应 `--ppp 1.0 / 1.5 / 2.0`） | 字形栅格化、1.1px 点阵采样、1px 线是否稳定、铬件是否被等比放大 | 与主题全交叉；与内容只抽两端 |
| 内容组合 | 空 / 单主题 / 深树 / 折叠 / 关系线 / 注解 / 编辑中 / 多选 / 概念图 / 卡片页 | 几何与语义（断行、角标挤压、箭头压字）**基本不随主题变**，随 DPI 只变「细节清晰度」 | 只在基准格各 1 场 + 2 类抽两端 |

一句话：**主题 × DPI 是唯一必须满格布的两维（4×3 = 12）；内容不乘进去，因为它的失败模式是几何与语义，
在任一主题下都会暴露；反过来主题/DPI 的失败模式（发灰、变粗、采样糊）必须在每一个主题、每一档 DPI 下看。**

### 2.2 四组矩阵（28 场）

**A 组 · 主题 × DPI 核心矩阵（12 场，占 12/28）**
- 取景：**同一份「审判内容」**——深树（三级 + 中英混排 + 长标题截断）+ 一条关系线 + 一个概要括号与一个
  边界 + 一个折叠节点 + 缩放条/小地图可见。一屏内同时能看到字阶、分支线、角标、圆点、点阵、铬件。
- 组合：`4 主题 × 3 DPI`。
- **CSS 视口恒定 `800×600`**（关键设计）：跨 DPI 比较铬件「屏幕恒定」必须让 css 尺寸一致，
  否则看到的是「窗口变小」而不是「DPI 变了」。物理像素 = `css × ppp`：

| DPI | ppp | 物理像素 | `MW_WINDOW_SIZE`（= css × ppp / 1.5，宿主缩放 1.5） |
| --- | --- | --- | --- |
| 100% | 1.0 | 800×600 | `533x400`（舍入，允许 ±1） |
| 150% | 1.5 | 1200×900 | `800x600` |
| 200% | 2.0 | 1600×1200 | `1067x800`（舍入，允许 ±1） |

- 为什么要 800×600：宿主物理上限 1920×1200，200% 档的 css 上限就是 960×600；取 800×600 留边距，
  三档都能真拍（X20 当年 2.0 档大窗口拍不了，就是没做这一步换算）。
- **不做换算会看到什么**（现成反例）：现有 `base-ppp2.0` 的基线 `shots/golden/shell-ppp2.00.png`
  是 1620×1080 物理——因为窗口物理尺寸不随 ppp 变，它的 css 只有 810×540；同一份内容在 100% 下 css 是
  1620×1080。也就是说：**不把 css 视口钉住，跨 DPI 比出来的是「窗口变小了」，不是「DPI 变了」**。

**B 组 · 关键内容组合（10 场，基准格 = `snow` × 150%，css 1620×1080）**
用户点名的十类内容各 1 场，只在一个主题/一档 DPI 下拍（几何与语义的判据与主题无关）：

| # | 内容 | 这一场要被抓出来的典型缺陷 |
| --- | --- | --- |
| B1 | 空画布 | 空态提示与点阵是否互相打架；四主题边界是否干净 |
| B2 | 单主题 | 单节点取景、卡片阴影/圆角、字阶基线 |
| B3 | 深树（20k 取样 + 5 级） | 分支线锥形宽度、层级缩进、长标题省略号 |
| B4 | 折叠 | 折叠圆点位置与计数角标、折叠后连线是否收干净 |
| B5 | 关系线 | 箭头屏幕恒定、曲线控制点、命题短语不压字 |
| B6 | 注解（概要 + 边界） | 括号与边框的层级、标签避让、跨节点跨度端点 |
| B7 | 编辑中 | 编辑环/光标与卡片的关系、占位提示不闪烁（截图终态） |
| B8 | 多选 | 多选框与选中底的叠加、与折叠圆点的层级 |
| B9 | 概念图 | 椭圆节点、关系线、检查器同屏（概念图是另一种画布语言） |
| B10 | 卡片页 | 只为「同屏一致性」抽检：画布 vs 卡片页的同一主题底色/字阶不打架 |

**C 组 · DPI 交互抽样（4 场）**
从 B 组挑两个「最怕 DPI」的内容，补两端 DPI（100% 与 200%）：深树（B3）与关系线（B5）。
理由：深树的 1px 分支线与字阶、关系线的 0.5px 箭头与命题短语，是「只在极端 DPI 才露」的两类。

**D 组 · 200% 窄窗专项（2 场）**
`200% × css 640×460 × {snow, ink}`。200% 最容易出现的不是「糊」而是**溢出与挤压**：
面板/缩放条/小地图在 640 逻辑宽下是否还放得下、文字是否被裁。用 snow（最亮）与 ink（最暗）两端覆盖对比度极值。

**合计：12 + 10 + 4 + 2 = 28 场；每场 `--tol 0` 连跑两遍 = 56 次比较。**

### 2.3 为什么不是 120 场，以及不拍哪些格子

- `4 主题 × 3 DPI × 10 内容 = 120 场 × 2 遍 = 240 次比较`，单轮矩阵约 40 分钟（按 stage-b 178 场 ×2 用
  ~26 分钟折算），且 120 格里绝大多数格子的失败模式被邻居完全覆盖——**这是付费买冗余**。
- 降维后的覆盖率论证：
  - 主题 × DPI 的 12 格全在（A 组）⇒ 任何「某主题在某 DPI 下发灰/变粗」都能被抓到；
  - 每类内容至少在 150% 出现一次（B 组）⇒ 几何/语义缺陷至少在一个 DPI 下暴露；
  - 最怕 DPI 的 2 类内容在 100%/200% 各出现（C 组）⇒ 「只在极端 DPI 才露」的两类不漏；
  - 200% 的**空间**极值由 D 组覆盖（窄窗是 200% 最真实的失败场景）。
- **明确不拍、并承认风险的格子**：

| 不拍的格子 | 风险 | 谁替它兜 |
| --- | --- | --- |
| `mist`/`sand` × 200% × 窄窗 | 暖色浅主题在 200% 窄窗下的细线对比 | 用 `ink` 200% 窄窗（暗端）+ `sand` 150%（暖端）兜；若判词觉得不足，P2 补 2 场 |
| 10 类内容 × 其余 11 个主题/DPI 格 | 某内容在某个特定主题下才难看 | 内容缺陷与主题无关是本文的假设；AI 判词发现反例时必须补格，不许拿假设当结论 |
| 卡片页 × 4 主题 × 3 DPI | 卡片页整页视觉 | 不属本门（N3）；X20 已过四主题外壳 |
| 编辑中 × 3 DPI | 光标/IME 细节 | 编辑态归 Stage D（N1） |
| 20k 满载 × 四主题 | 性能类视觉（帧时间、分块重建） | 性能归 M12 系列证据，本门不看 |

### 2.4 场景命名与登记

- 命名：`x30-<组>-<内容或主题>-p<DPI>[-narrow]`，例：`x30-a-ink-p200`、`x30-b-deep`、
  `x30-c-rel-p100`、`x30-d-ink-p200-narrow`。
- 基线目录：`shots/golden/<场景名>/shell-ppp<?>.<??>.png`（沿用 harness 现有命名）。
- 门脚本：`scripts/x100-stage-c-x30-gate.ps1`（**未创建**）；复用 `scripts/golden-matrix.ps1` 的
  「每场独立 `APPDATA`/`LOCALAPPDATA` + 场景表抽自门脚本」写法，不另起一套。
- **不登记进 `scripts/x100-stage-b-gate.ps1`**（N4）：stage-b 是回归门，X30 是视觉门；混在一起会让
  「回归零差异」与「人工判词」两种语义搅在一起。

### 3.2 人工项（判词表，22 格）

- **A 组 12 格**（四主题 × 三 DPI）逐格判 5 项：
  1. **层级可读性**：中心 / 一级 / 子主题的字号、字重、颜色差能不能一眼分出三级；深树里会不会塌成一片。
  2. **对比度**：浅主题在 100% 与 200% 下细线（分支线、边框、点阵）、角标、次要文字是否吃力；
     暗主题反过来看「是否发灰、发雾」。
  3. **笔触一致性**：分支线锥形、圆角/椭圆轮廓、点阵密度在 100%→200% 之间观感一致
     （不是「200% 变粗一倍」也不是「200% 变细」）。
  4. **铬件屏幕恒定**：缩放条/小地图/检查器占同一块 css 面积；200% 下没有被等比放大。
  5. **内容正确性**：中英混排断行、长标题省略号、角标不压字、关系线箭头不压在文字上。
- **B 组 10 格**各判与本内容相关的那几项（B3 判 1/3/5，B5 判 4/5，B10 判主题一致性……逐格在判词表里写死）。
- 判词格式：每格 `✅ / ❌ + 一句理由（看到什么、在哪张图、什么症状）`；**不许只写「看起来不错」**。

### 4.3 为什么不并入 stage-b

1. **语义不同**：stage-b 判「与基线逐字节一致」，X30 判「人看合不合格」；混在一起会让门失败时说不清是回归还是审美。
2. **成本不同**：178 场已经 26 分钟；再加 28 场 ×2 会拖长每次回归。
3. **变更频率不同**：X30 基线只在阶段收口时重拍；stage-b 基线随每个包动。

## 5. 门的通过 / 不通过怎么写

### 5.1 机器项与人工项分开写

```text
X30 MATRIX PASS 56/56                       # 28 场 × 2 遍，--tol 0 零差异
MACHINE ITEMS PASS (M1–M6)                  # 尺寸 / 双跑 / 铬件 bbox / 四边 / 对比度 / 不重拍
  或者 MACHINE GATE FAIL: M3 chrome bbox 200% sand 缩放条 css 宽 68 → 74（差 6px）
HUMAN VISUAL GATE PASS 22/22                # 12 格 A 组 + 10 格 B 组，逐格 ✅
  或者 HUMAN VISUAL GATE FAIL 19/22: A-mist-p200（细线发灰）、B3（省略号压分支线）、B5（箭头压字）
X30 GATE PASS                               # 仅当上面两段都 PASS 且判词有签字/授权
```

- **机器项过了、人工项没过 = 门没过**；反过来也一样。**不许用「机器全绿」代替判词**。
- 失败必须写清：哪一场、哪个判据、看到什么（图路径 + 症状一句话），并落到 `gate.md` 的「不通过项」表。
- 门未通过时开修复包（不进 X30 本身），修复后**重跑全门**，不局部补拍（局部补拍会让判词失去可比性）。
- 状态词只用六个：本文件现在 `未开始`；矩阵跑完未判词 = `进行中`；判词全过 = 门 `PASS` 但包状态仍是
  `已实现`（`已验证` 需实机 DPI + 拼音，见 N6）。
