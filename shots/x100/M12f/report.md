## 1. 开工前审计

| 口径 | 现状（`M12d` §5.2 / `M12e`） | 结论 |
| --- | --- | --- |
| P7「布局函数计时」 | p50 13.00 / p95 13.90 / max 15.55ms，**已达标** | 布局本身不再是瓶颈 |
| P7 端到端（含 `Command` + 账本） | 中位 **16.7ms**、p95 18.4ms | **仍差约 0.7ms 到 16ms 线** |
| 差额在哪 | `M12d` §6 已定位：不在 `[scene]` 里，而在 `memo_nodes = nodes.clone()` 与命令本身 | 本轮只动前者 |

`build_scene_cached` 每帧末尾都做一次 `let memo_nodes = nodes.clone();`——两万个 `SceneNode`
整份克隆（注释自己写着「约 1ms」）。这份克隆**唯一的目的**是让下一轮能复用上一轮的节点表，
而本帧返回的 `Scene` 同样持有这份表：两边都在只读地看同一批数据，却各存了一份。

## 2. 非目标

- 不改布局算法、不动 `LayoutMemo` 的复用判据（那是第 11、14 轮已经收口的东西）。
- 不动 `Command` / 撤销栈的复制成本（那是另一本账，且属领域层语义）。
- 不改任何像素：本轮通过后**所有 golden 必须零漂移**——这是本包唯一的外观断言。
- 不碰概念图路径（节点数远小于 20k）。

## 3. 验收场景

1. **端到端达标**：`perf_scene` 的「20000 改字重建(缓存)」中位 **≤ 16ms**，且 p95 也在预算内；
   同一轮跑前后各测一次（同一台机、同一命令），差值写进报告。
2. **像素零漂移**：stage-b + stage-cm 两道门双跑 `--tol 0` 全过，一张基线都不重拍。
3. **语义等价**：`Scene` 的公开读取方式（`scene.nodes[i]`、`scene.ids[i]`、`scene.index`、
   `scene.find()`）在调用方看来不变；只有内部存储从「独占持有」变成「共享持有」。
4. **复用未被破坏**：`MW_LAYOUT_LOG` 里 `reused=19999` 仍然成立（共享持有不能把复用路径改坏）。

## 4. 预计证据

- 前后对比表（中位 / p95，各 3 轮 × 40 样本）。
- 单测：新增一条「两帧场景共享同一份节点存储」的判据（`Arc::strong_count` 或指针相等），
  钉住「重建时不再整份克隆」这件事本身。
- 两道门绿、测试数只增不减、clippy 新增 0。
