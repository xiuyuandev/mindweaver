## 1. 工作量结论

### 1.1 一句话回答

**这三项不是 3 轮能做完的，也不是“换一套皮肤”。**
按可验收的深度，需要 **34 个工作包**，分 **4 批**、**4 道人工门**；
相对原 X61–X70、X81–X82 共 12 轮的排期，**净新增约 22 个等效轮次**；
纯 AI 连续开发约 **3–4 周（19–27 个 AI 工作日）**，加上 4 次人工验收，日历时间约 **5–6 周**。

### 1.2 为什么不是 3 轮

| 做法 | 包数 | 结果 | 判定 |
| --- | --- | --- | --- |
| 只换颜色、字号、圆角 | 12–14 | 截图第一眼变干净；编辑、IME、长文、10k 卡片、拖拽仍坏 | **打回**：过不了 5 分钟任务与长文/大库场景 |
| 做到“演示能看” | 24–26 | 默认状态能看；长文档、20k 大纲、10k 卡片、批量操作露馅 | **不够**：只能记“已实现”，不能记“已验证” |
| 本次推荐 | **32–36** | 共享底座 + 三个内容表面 + 交叉联动 + 全矩阵收口 | **采用 34** |
| 继续扩功能 | 40+ | 滑向表格、AI、云同步、模板市场，核心体验继续欠账 | **禁止**：超出三界面范围 |

## 2. 全局纪律（34 个包都适用）

1. **先文档后代码**：每个包开工前，先在 `shots/x100/CER-XX/report.md` 写“范围 / 非目标 / 验收场景”；
   写完再动代码。设计有冲突，先改 `docs/28` 或本文，不允许在代码里“先斩后奏”。
2. **只改该包范围**：不顺手重做画布、检查器、标题栏、开始页；不引入新依赖、新 crate、新构建工具；
   不改 `.zmind` 格式；不做迁移；不新增云/账号/AI/协作。
3. **文档变更只走 Command**：大纲、卡片来源、反链、标签等所有文档写入必须走 `mw_core::Command`
   与撤销栈；禁止直接改 `Document`。笔记正文仍走 `NoteStore::upsert`。
4. **中文是验收项**：每个涉及输入的包都要用微软拼音验证组合态；CJK 禁则、中英混排、
   200% DPI 不能只靠截图“看着行”。
5. **禁止复制竞品资产**：幕布、Typora、Bear、flomo、Craft、Linear 只提供原则与方向；
   不复制字体、图标、主题、文案、截图素材、布局参数。像素值以 `docs/28` 为准。
6. **没做就是没做**：状态只用 `未开始 / 进行中 / 已实现 / 已验证 / 阻塞 / 延后`。
   没有四类证据与人工判词，只能写 `已实现`。
7. **不提交 git**，除非用户明确要求；不清理、不重置、不 stash 现有未提交工作。
8. **一次只开一个包**：同一时刻只允许一个 CER 处于 `进行中`；需要并行时先拆清文件边界，
   并在两个报告里互相引用。

## 3. 完成定义（每个包都按这个判）

一个工作包只有同时满足以下 7 条，才能从 `进行中` 改为 `已实现`：

1. **代码**：实现落在既有 crate 边界内；没有新增依赖/crate；没有绕过命令层。
2. **行为**：纯函数单测或 `MW_GOLDEN_INPUT` / `MW_TRACE` 脚本覆盖主路径 + 至少一个边界；
   输入类场景必须有 IME 或键盘脚本。
3. **视觉**：按 `docs/28` 要求的主题/DPI/窗口矩阵实拍；有参考图或设计依据；
   截图停在稳定帧，不截 hover 残留或动画中间态。
4. **回归**：受影响 golden 按 §5 协议重拍并双跑 `--tol 0`；未受影响场景逐字节不变；
   旧文件读取/保存/往返至少跑一次；结构操作至少跑一次撤销/重做。
5. **工程**：`cargo fmt --all -- --check`、相关测试、`cargo clippy -p mw-shell --all-targets`
   新增 0、release 构建通过。
6. **文档**：`shots/x100/CER-XX/report.md` 写清范围、变更、验证、未做、风险；
   `manifest.json` 记录场景、哈希、DPI、主题、脚本；必要时回填 `HANDOFF.md`。
7. **人工判词**（仅门包）：按 `docs/28` §9.3 的八条判词逐条记录；用户未确认时只能写 `已实现`。

`已验证` 只在人工门通过后使用；门未通过时，相关包保持 `已实现` 或 `阻塞`。

## 5. golden 与基线协议（B2 会重拍外观）

B2 是有意的外观重构，旧基线会变；但“会变”不等于“随便变”。

1. **开工前留旧账**：对每个将受影响的场景，先记录当前 PNG 的 SHA-256、尺寸、逻辑 DPI，
   写进该包 `report.md`。没有旧哈希，不许 `--update`。
2. **只重拍受影响场景**：一次只 `--update` 本包涉及的最小场景集；禁止全量重拍“顺手统一”。
3. **记录漂移**：写清变化原因、bbox、像素差、最大通道差；预期内的整体重排要写“预期”，
   预期外的局部差异要查清再重拍。
4. **双跑 `--tol 0`**：重拍后连跑两次，必须 0 差异；不 0 就修确定性，不许放宽容差。
5. **未受影响场景逐字节不变**：如果变了，先查是不是共享组件/令牌被误改。
6. **新场景命名**：按 `docs/28` §5.10 / §6.11 / §7.10 的名字；默认场景至少覆盖
   1.0/1.5/2.0 DPI 与四主题；输入态场景必须有脚本与 `--warmup`。
7. **不拿 golden 当审美证据**：golden 只证明稳定；好看/好用必须有人工判词。
8. **旧基线不删除**：被替换的基线在报告里留旧哈希与旧图路径；需要回退时能找回。

`report.md` 固定小节：

1. **范围**：本包做什么，对应 `docs/28` 哪一节。

4. **验证**：行为/视觉/回归/工程四类证据，附命令与结果。
5. **未做/已知偏差**：没做的、只做一半的、性能未达标的，逐条写。
6. **风险**：下一包/下一批可能踩的坑。
7. **人工判词**：门包才填；用户未回复写“待用户”，不得代写通过。
