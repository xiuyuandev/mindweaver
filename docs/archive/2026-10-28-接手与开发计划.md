## 2. 策略：三条原则

1. **一次只开一道门。** 门未过只修当前批。B2 与 P/M 轨可以并行，但每条轨内部不跳批。
2. **先让机器说真话，再让人说好不好。** 门红的时候不做审美判断，先补基线；
   基线绿了再请人看。机器门只证明稳定，不证明好看。
3. **每包收工必须同时留下四样东西**：`report.md`、`manifest.json`、可复跑的判据、`STATUS.md` 的更新。
   少一样就不算收工——这是 2026-10 这一轮欠账的主要来源。

## 4. 每个工作包的执行模板

```
1. 读合同：docs/29 或 docs/31 对应行 + docs/28 / docs/30 对应章节
2. 写 shots/x100/<ID>/report.md：范围、非目标、验收场景、预计证据
3. 写测试/输入脚本（输入类必须覆盖 IME）
4. 实现（文档变更走 Command；不改 .zmind）
5. 跑门槛：fmt → clippy（新增 0）→ scripts/test.ps1 → 碰外观则 golden 双跑
6. 回填：report + manifest.json + docs/x100/log/ 漂移量 + docs/STATUS.md
```

**收工前自问三句**：
- 合同里的每一条，我是「做了」还是「没做」？没做的写进 report 的「未做」。
- 我的证据能不能让别人在另一台机器上复跑？命令写了吗？
- `STATUS.md` 的那一行，现在读起来还准吗？

## 6. 风险与对策

| 风险 | 后果 | 对策 |
| --- | --- | --- |
| 工作树仍未提交 | 一次误操作丢数周工作 | 阶段 0.3 立刻 checkpoint；之后每开一道门提交一次 |
| 门红被当成绿 | 后续结论全建立在过期基线上 | 每次引用门状态前先看 `STATUS.md` §1 |
| 合同条款被「差不多」掉 | G-B2-2 必挂 | report 必须列「未做」，STATUS 必须带缺口 |
| 并行轨抢同一文件 | 合并冲突、互相覆盖 | `design.rs` 改动一次性做完；共享文件同一时间只给一条轨 |
| 实机 IME 一直不测 | 中文四痛点无法闭环 | 阶段 2 开门时安排一次真人微软拼音测试 |
| 20k/10k 性能最后才测 | 返工 | CER-20 与 CER-25 各自带性能日志，不等 B2-D |
| 一次性脚本越堆越多 | `scripts/` 40+ 个 `tmp-*.ps1` | 每轮收工把一次性脚本移入 `scripts/oneoff/` 或删除 |

## 7. 明确不做

- 不跳 B2-B 直接做 B2-C，不跳 G-B2-4 直接做 Stage C。
- 不做「换肤式」B2；不做双栏预览；不做彩色标签墙；不做树线大纲。
- 不引入新依赖、新 crate、新构建工具；不改 `.zmind` / `Node` / `NoteCard` 字段
  （已批准的两个例外见 `AGENTS.md` §8）。
- 不在门红时重拍基线来「让它变绿」——先判断是环境、是过期基线，还是真回归。
- 不清理/重置用户未提交的工作，不擅自提交 git。

## 9. 什么算「接手成功」

1. `scripts/x100-stage-b-gate.ps1` 双跑全绿，且场景数与 `STATUS.md` 一致。
2. `docs/STATUS.md` 的数字与实测一致；其它文档不再各写一份数字。
3. 工作树有一次 checkpoint 提交，之后每个门有提交。
4. G-B2-2 已开；无论过没过，缺口都按包记在 `STATUS.md` 里。
5. 新来的人按 `AGENTS.md` → `HANDOFF.md` → `STATUS.md` 的顺序，30 分钟内能说清
   「现在在哪、下一步做什么、为什么」。
