## 4. 性能设计要点（架构落地，供开发对照）

- **视口虚拟化**：仅挂载视口内 + 200px 缓冲的节点 DOM；滚动中复用节点元素池；
- **增量布局**：脏标记自下而上传播，只重排受影响子树；布局纯函数 + 结果缓存（输入指纹=子树版本号）；
- **文本测量缓存**：LRU（键=文本+字号+最大宽，容量 10,000 条），中文长文本重复测量是最大热点；
- **渲染分层**：SVG 分静态层（背景/未变子树）与活动层（编辑/选中/拖拽），`will-change` 限定在活动层；
- **批量提交**：命令补丁在 rAF 内一次性应用；连续事件 16ms 合并；
- **后台化**：保存、导出、索引重建、缩略图生成全部离开主线程；导出时序列化场景图传值（结构化克隆），避免与 UI 争抢；
- **大文档降级**：见 §6；**禁止**用"隐藏动画"以外的功能性降级（功能对任何档位一致）。

## 8. 性能测试基建

- **criterion 基准**（Rust）：命令执行、撤销、序列化、索引重建、容器读写，每样本跑基准集写入 `docs/perf/` 趋势页（CI 生成）；
- **运行时探针**（2026-10-18 已建成）：`MW_STATS=1` 显示右上角 FPS/帧耗时/UI 耗时/可见节点/缩放/省渲染/过渡态卡片；`MW_STATS_LOG=<path>` 每 60 帧写一行 TSV（240 帧滚动窗、渲染间隔 >250ms 时清窗）；`MW_PERF_LOG=<path>` 写启动里程碑（`process_start`/`shell_new`/`doc_open_start`/`doc_open`/`first_ui`/`first_canvas`）。默认不设环境变量时零开销、不落盘；
- **真实输入探针**：`scripts/m5-perf.ps1` 隔离 `APPDATA`、等待真实主窗口（≥600×400）、注入 Win32 滚轮缩放 + 中键拖拽、截图、解析最后一条汇总并按 P5 阈值打印 PASS/FAIL；`-StartPage` 测 P2，`scripts/m5-memory.ps1` 按分钟采私有内存/工作集（P13）；
- **样本语料**：`node scripts/make-sample.mjs --nodes=N` 生成任意规模的合成文档（BFS 树、长文本、标签、图标、备注；大文档用 `mindmap` 布局），已产出 5k/10k/20k 三份供基准与手动压测复用。仓库仍保留 3 节点跨实现互操作样例；
- **编辑/搜索基线**：`cargo run -p mw-core --release --example perf_scene` 现在同时输出 P8 全量重排、P7 代理、P6 改字重建与 P9 撤销/重做 + 重建，末尾跑 3 次 20k 冷缓存与二次拼音查询（P12）；`cargo run -p mw-format --release --example perf_save -- <doc.zmind> [runs]` 量 5k/10k/20k 的加载与保存（P10）。
- **导出基线（P11）**：`MW_OPEN=<doc> MW_EXPORT_BENCH=<out.png|out.pdf> [MW_EXPORT_SCALE=2] <release exe>`。应用在首帧画布后克隆场景并走与 `Ctrl+E` 相同的 `export_job::start` 管线，打印 UI 快照耗时、工作线程耗时、提交→完成墙钟、像素尺寸、字节数与生效比例，然后自动退出；用后缀选择 PNG/PDF。这是端到端的工作线程计时，不含保存对话框。
- **回归纪律**：每夜 bench 若任一指标劣化 >10% → CI 黄牌，milestone 内必须处理或书面豁免（记 ADR）。当前 P15 未测，P13 已 PASS（10k 五分钟 284.4–287.9MB，余量 12.1MB，见 §9.1）。

**口径说明**：这里报的是 Windows 提交内存（`PrivateMemorySize64`），不是任务管理器「内存」列的 RSS（那是 `WorkingSet64`）；两者都列出了。单机单次采样，未做强制 GC / 碎片分析；10k 语料是 `logicRight`（47% 可见），可见比例不影响内存口径，但不能拿来当 P5 证据。

## 10. P6–P12 补充实测（2026-10-18）

**目的**：P1–P5、P13、P14 已有真实窗口数据（§2.1、§9）；这一轮把**命令、布局、撤销、保存、搜索**先量到核心层，明确哪些过线、哪些只是代理口径、哪些还没有实现。所有数字来自 release 示例，机器与语料同 §1/§2.1；**不含 GPU 合成与 egui 绘制**，是 UI 端到端时间的下界。

### 10.1 布局 / 编辑 / 撤销（`perf_scene`）

| 项 | 5k 中位 | 5k p95 | 预算 | 判定 |
| --- | --- | --- | --- | --- |
| `build_scene` 全量（P8） | **8.4ms** | 16.2ms | 120ms | ✅ |
| 仅 `compute_layout` | 1.8ms | 2.5ms | — | — |
| 改字 + `build_scene`（P6 代理） | 8.1ms | **9.8ms** | 50ms | ✅ |
| 撤销 + `build_scene`（P9） | 7.1ms | **9.0ms** | 30ms | ✅ |
| 重做 + `build_scene` | 6.4ms | **8.0ms** | 30ms | ✅ |

- P6 的数字是「`apply(SetText)` → 全量重建场景」，真实壳层只会在脏时重建，所以这是**上界**而不是端到端测量；UI 线程统计（§2.1 P5）给出的 p95 1.78ms 是常帧，不含命令提交那一帧的重建。
- **P7 没有增量布局**：上表「改字重建」就是全量 `build_scene`，9.8ms 虽然低于 16ms，但口径不成立。真正的增量重排（受影响子树 ≤200 节点）仍未实现，M5 不能据此判绿。
- P9 的撤销本身接近 0ms（只回滚一个节点的 `ChangeSet`），上表时间主要是随后的场景重建；在 5k 规模下组合预算 30ms 仍有余量。

### 10.2 保存与自动保存（`perf_save`，P10）

| 文档 | 加载 | 整份保存 p50 / p95 | UI 线程快照 p50 / p95 |
| --- | --- | --- | --- |
| 5k（约 0.7MB） | 10.4ms | 13.5 / 14.0ms | **2.1 / 2.7ms** |
| 10k（1.3MB） | 26.6ms | 24.6 / **27.4ms** | **4.4 / 4.7ms** |
| 20k（2.6MB） | 63.7ms | 49.0 / 50.3ms | **8.9 / 9.2ms** |

- 保存路径与自动保存完全相同（`mw_format::save`：JSON → ZIP → 原子替换 + `.bak`），整份保存全部在工作线程；**150ms 预算以工作线程耗时计，p95 27.4ms（10k）远低于上限**。
- 自动保存改为后台写线程（`autosave::Background`，2026-10-18）：UI 线程只克隆一份 `Snapshot`（节点表 + 元数据，不含撤销栈/检索缓存），序列化、压缩、磁盘 IO 在常驻线程完成。快照实测 p95 **4.7ms（10k）/ 9.2ms（20k）**，低于 60fps 的 16.7ms 帧预算；**没有跨帧的长任务**。严格说 UI 线程仍有这几毫秒的克隆成本，不是数学意义上的「0」，但不再出现此前 26–52ms 的整帧阻塞。
- 写入策略：同一时刻最多一个在途任务；在途期间的新修订只保留**最新一份**排队，恢复点不需要中间版本。`invalidate`（正本保存后）会删槽位并记住「在途写完成后不能再复活」；切文档/打开/恢复用代际号隔离旧结果，避免 A 文档的修订号冒充 B。
- 真实窗口抽查（2026-10-18）：编辑后 3 秒 `.autosave/<stem>.autosave.zmind` 出现且比正本新；随后 Ctrl+S，槽位被删除、正本 mtime 前移。后台写失败（磁盘满/无权限）静默跳过，由下一个编辑周期重试。
- 未做：整帧卡顿的端到端采样（目前以快照克隆成本 + 单测论证）；非活动标签仍不自动保存；恢复点写盘期间退出最多等 1.5s（`on_exit` 的 `settle`）。

### 10.3 拼音检索（P12）

`synthesize 20k` → 新建 `SearchIndex`（缓存为空）→ `Document::search("xing")`，三次独立文档；同一文档随后再查一次记录热缓存：

| 次数 | 首次查询（冷） | 二次查询（热） | 命中 |
| --- | --- | --- | --- |
| 1 | 38.2ms | 14.3ms | 0 |
| 2 | 41.7ms | 11.7ms | 0 |
| 3 | 40.6ms | 13.4ms | 0 |

- **P12 PASS**：冷查询 **38.2–41.7ms**，低于 100ms 预算；热查询 **11.7–14.3ms**。
- 优化（2026-10-18）：`pinyin` 的 `plain()` 本身返回 `&'static str`，读音改为固定数组，不再逐字 `Vec<String>` + `to_lowercase()`；单读音字符就地追加，不再每字符克隆整份 `Key`；ASCII 字母数字直接入键；原文无大写时借用原文匹配，省掉每节点一次 `to_lowercase` 分配。缓存上限 8000 → 32000，20k 文档首次搜索后键可全量驻留，不再每次输入整体清空重建。
- 代价：20k 文档首次搜索后缓存常驻（短文本估算 8–12MB，**未单独计量**）；P13 的五分钟采样不触发搜索，内存数字不受影响。
- 结果仍按分数降序、同分按文档前序排序，`truncate(500)` 不变；拼音音节边界、多音字变体与原文大小写不敏感均有单测覆盖。

### 10.4 导出 PNG/PDF（P11，工作线程）

**量法**：release 构建，`MW_OPEN=<doc> MW_EXPORT_BENCH=<out> [MW_EXPORT_SCALE=2]`。首帧画布后克隆 `Scene`/`Theme`，走与 `Ctrl+E` 完全相同的 `export_job::start` 任务；UI 线程只做轮询（在途每 120ms 催一帧），排版、离屏渲染、PNG/PDF 编码与写盘都在命名字线程 `zmind-export`。工作线程自建 `TextEngine` 与一次性 `Compositor`（画布那台不能借：`Compositor::render` 会重建目标纹理，而画布纹理正被 egui 采样），写同目录 `.part` 成功后原子改名。

| 文档 | 节点 | UI 快照 | 工作线程 | 提交→完成 | 产物 | 生效比例 |
| --- | --- | --- | --- | --- | --- | --- |
| 3 节点互操作样例（PNG） | 3 | 0.01ms | **38.8ms** | 46.3ms | 910×300，33,357 B | **2.000×** |
| 3 节点互操作样例（PDF） | 3 | 0.01ms | **30.7ms** | 38.7ms | 910×300 页，19,354 B | **2.000×** |
| 合成 5k（BFS/mindmap，PNG） | 5,000 | 0.94ms | **70.9ms** | 107.6ms | 206×8192，1,490,462 B | 0.057× |
| 合成 20k（BFS/mindmap，PNG） | 20,000 | 4.00ms | 63.8ms | 101.4ms | 56×8192，892,312 B | 0.014× |

- **P11 的时间与线程预算通过**：5k 工作线程 **70.9ms** ≪ 3.0s，整个导出不在 UI 线程执行；UI 只付出 0.94ms 的场景克隆。提交→完成多出的约 37ms 是线程启动、120ms 轮询粒度与退出收尾，不是 UI 阻塞。
- **诚实口径（2× 被护栏缩限）**：5k/20k 的 BFS 合成语料是 1:40 及更极端的长宽比（世界尺寸约 3,614×143,719），字面 2× 需要 7,228×287,438 像素。`png_size` 的 8192 单边 / 32MP 总面积护栏把它按比例收小到 0.057× / 0.014×，所以这两张产物**不是字面 2×**，也不能用它们的耗时代表「32MP 满幅 2×」的成本。真实 2× 由 3 节点样例验证（2.000×、910×300）。要量满幅 2× 需要一份能塞进 32MP 的 5k 场景；现有自动布局不做二维紧凑排布（mindmap 是放射树，logicRight 叠成高柱），本轮没有合成出这样的语料。
- **PDF**：同一工作线程管线，`Kind::Pdf` 只换编码器（`export_pdf::encode`，页面尺寸按世界尺寸 96dpi→72pt），仍是嵌位图、文字不可选，与 M4 口径一致。bench 用输出后缀选格式。
- **产物校验**：3 节点 PNG 已逐像素目检——根/两个子节点、优先级图标、备注角标、主题底色与连线均正确；PDF 由编码器单测（xref 字节偏移、SMask/Flate）与成功落盘验证，本机无 PDF 渲染器，未做页面目检。失败路径删除 `.part`，进程中断不会留下半份成品。
- **边界**：导出线程与画布共用同一个 wgpu `Device`/`Queue`，导出期间画布的 GPU 提交会与导出排队；本轮只测了 UI 克隆与总耗时，没有做导出期间的逐帧卡顿采样。单飞限制下重复导出会提示等上一张完成。
